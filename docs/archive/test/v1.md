Below is a **complete testing + canary rollout plan** tailored for a **Kubernetes Gateway API implementation based on the Rust proxy framework**, with an engineering-oriented approach.

Let me start with the conclusion:

> This project cannot just test “whether HTTP works.”
> You need to cover at least 6 tracks simultaneously:
> **1) Gateway API semantics and conformance**
> **2) Controller/reconciler behavior**
> **3) Rust proxy data plane protocol correctness**
> **4) Security**
> **5) Performance/capacity/stability**
> **6) Canary release and rollback mechanisms**

# 1. Do the Most Important Thing First: Define “What Do You Actually Support”

Before starting comprehensive testing, produce a **Support Matrix** first, otherwise the test scope will spiral out of control.

## 1.1 What You Need to Define

Following the official Gateway API approach, clearly define:

- Target Gateway API **bundle/version**
- Supported resources:
  - `GatewayClass`
  - `Gateway`
  - `HTTPRoute`
  - `GRPCRoute`
  - `ReferenceGrant`
  - `BackendTLSPolicy`
  - `TLSRoute`
  - `TCPRoute`
  - Mesh/GAMMA (if supported)
- Support level for each feature:
  - **Core**
  - **Extended**
  - **Implementation-specific**
- For each feature, whether:
  - Enabled by default
  - Requires feature gate
  - Requires special configuration
- The capability boundary you want to publicly claim as supported

## 1.2 Why This Step Must Come First

The Gateway API official documentation explicitly emphasizes:

- **Conformance is version-specific**
- To claim conformance, **there must be no skipped tests**
- Extended features can be unsupported, but **if supported, behavior must be consistent**

Therefore, your test plan must first be designed around “which features I want to claim,” rather than expanding without boundaries.

## 3.1 Gateway API Semantics Testing

## A. GatewayClass / Gateway Basic Behavior

### What to Test

### GatewayClass
- Whether the controller only recognizes its own `controllerName`
- Whether the `Accepted` condition is correct
- Whether GatewayClasses not belonging to this controller are not incorrectly processed
- `parametersRef`:
  - Exists
  - Does not exist
  - kind not supported
  - Invalid content
- Whether the handling strategy for multiple GatewayClasses with the same controllerName aligns with your design

### Gateway
- Create/update/delete
- Listener add/delete/modify
- Address allocation
- `Programmed` / `Accepted` / `ResolvedRefs` condition
- Whether `observedGeneration` follows object version changes
- Whether `Gateway.spec.infrastructure` labels/annotations propagate downward to generated infrastructure
- Whether generated Deployment/Service/LB resources are consistent and idempotent

### Key Edge Cases
- Listener hostname conflicts
- Listener port/protocol conflicts
- TLS listener invalid configuration
- Secret does not exist / malformed
- Cross-namespace certificate ref with/without `ReferenceGrant`

### Acceptance Criteria
- Status conditions are accurate
- reason/message is readable
- Configuration changes are eventually consistent
- No orphan resources
- Reconcile is idempotent

## B. Route Attachment / Cross-Namespace Binding

This is one of the most error-prone areas of the Gateway API.

### What to Test
- Route binding to Gateway in the same namespace
- Route cross-namespace binding
- `allowedRoutes.namespaces.from`
  - `Same`
  - `All`
  - `Selector`
- selector matched / not matched
- Route kind restriction
- `parentRefs`:
  - name
  - namespace
  - `sectionName`
  - `port` (if supported)
- Whether binding is rejected when the two-way handshake is not satisfied

### Required Test Scenarios
- Gateway allows, Route points -> Success
- Gateway does not allow, Route points -> Rejected
- Route points to non-existent Gateway -> Should not incorrectly update state outside its own scope
- Whether binding relationships are recalculated in real-time after namespace label changes
- Whether cross-namespace backend/cert references are recalculated in real-time after `ReferenceGrant` add/delete

### Important Reminder
The official security model emphasizes that cross-namespace must have a **handshake model**:
- Route binding to Gateway: `allowedRoutes` + `parentRefs`
- Referencing backend/secret: `ReferenceGrant`

This must be thoroughly tested.

# 12. Canary Rollout Plan

For a Gateway implementation, I recommend splitting the canary into **control plane canary** and **data plane canary** two parts.

---

## 12.1 Control Plane Canary

### Safest Approach
Use an **independent GatewayClass** for canary, for example:

- Stable: `aether-gateway`
- Canary: `aether-gateway-canary`

Only migrate a small portion of Gateways to the canary GatewayClass.

### Benefits
- Does not immediately impact the entire cluster
- Can migrate gradually by namespace / business line / domain
- Rollback is very simple

---

## 12.2 Data Plane Canary

### Recommended Approach
**A separate Gateway instance / Service / LoadBalancer** as the canary data plane, rather than mixing old and new versions behind the same Service.

### Why
Gateway is the ingress traffic plane. Directly mixing pods, although simple, has issues:
- Configuration compatibility issues are hard to troubleshoot
- Inconsistent long-lived connection behavior is hard to analyze
- Observability and rollback are not clean enough

### Better Canary Approach
1. First shadow / mirror traffic
2. Then switch to low-risk domains or low-risk namespaces
3. Then do 1% / 5% / 10% / 25% / 50% / 100%

If it is application traffic splitting, you can combine with HTTPRoute weighted backend;
If it is the **gateway implementation itself** canary, it is more recommended to split at the LB / DNS / independent GatewayClass dimension.

---

## 12.3 Recommended Canary Steps

### Stage 0: Internal Validation
- Only accept test domains
- Only accept synthetic traffic

### Stage 1: Staging Shadow
- Mirror production traffic without returning results to users
- Compare response differences between stable and canary versions

### Stage 2: Single Business, Low-Risk Namespace
- 1 domain
- 1 namespace
- 1 Gateway

### Stage 3: Small Traffic
- 1%
- 5%
- 10%

### Stage 4: Expand Scope
- 25%
- 50%

### Stage 5: Full Rollout
- 100%
- Keep rollback window 24h~72h

---

### Business Metrics
- 2xx/4xx/5xx ratio
- gRPC `UNAVAILABLE` / `DEADLINE_EXCEEDED`
- WebSocket connection success rate
- Request timeout rate

### Performance Metrics
- p95 / p99
- TLS handshake latency
- upstream connect latency
- config propagation latency

### Stability Metrics
- pod restart
- Continuous memory growth
- fd growth
- Abnormal retry rate
- Abnormal backend resets

### Control Plane Metrics
- reconcile error
- Abnormal status updates
- Abnormal `Accepted/Programmed/ResolvedRefs` ratio

---

## 12.5 Rollback Conditions

Recommend pre-defining thresholds, for example:

- 5xx increase over baseline > 0.5%~1%
- p99 increase over baseline > 20%
- gRPC deadline error significantly elevated
- WebSocket connection success rate drops
- Gateway / Route status anomalies increase
- Controller error rate continuously rising
- Memory/FD continuous leakage

### Rollback Actions
- LB/DNS weight back to 0
- Canary GatewayClass stops taking over
- Helm rollback / image rollback
- Scale down canary data plane
- Restore stable controller
